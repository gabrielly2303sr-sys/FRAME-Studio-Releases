# FRAME Studio 2.4.15 — Advanced Effects release kit

FRAME Studio is an Electron-based local video and motion-graphics editor. This kit adds **in-app update checks** for the installed Windows NSIS build and Linux AppImage, using the public GitHub Releases repository:

`gabrielly2303sr-sys/FRAME-Studio-Releases`

## What auto-updates and what does not

- **Windows Setup installer (NSIS):** checks for updates on startup, prompts before downloading, then prompts to restart/install. The update metadata must be attached to each GitHub Release (`latest.yml`, setup `.exe`, and `.blockmap`).
- **Linux AppImage:** uses `latest-linux.yml` from GitHub Releases. Keep the AppImage in a folder the current user can write to; replacing an AppImage in a root-owned directory cannot be done automatically.
- **Windows Portable EXE:** remains available for manual use, but electron-updater does not update the portable build. Download the latest portable EXE yourself.
- **Linux DEB/RPM:** available for wider distro compatibility, but users update these packages manually through a newer package / their package workflow. In-app update applies to AppImage.
- **The old 2.4.11 builds cannot magically gain updater code.** The first version containing this updater must be installed once manually (2.4.13); future compatible versions can then update in-app.
- **The existing source ZIPs/build kits are not themselves app update packages.** Keep them as optional source/install materials, but publish real NSIS/AppImage binaries and their metadata for auto-updates.

The updater validates download hashes through the metadata generated by Electron Builder and communicates with GitHub over HTTPS. If no internet is available, update checking fails quietly and the current app remains usable.

## Windows: build an auto-updatable installer

1. Extract this source kit.
2. Open `frame-studio-linux` and run `BUILD-WINDOWS.bat` on Windows with Node.js 22+ and internet access.
3. After a successful build, upload these generated files to the GitHub Release whose tag matches the package version (for example, tag `v2.4.15`):
   - `dist/FRAME-Studio-2.4.15-Setup-x64.exe`
   - `dist/FRAME-Studio-2.4.15-Setup-x64.exe.blockmap`
   - `dist/latest.yml`
4. The installed NSIS build checks the `latest.yml` attached to the latest public GitHub Release. Future releases must include the new setup EXE, blockmap and `latest.yml`.

The portable EXE can also be built with `npm run build:win:portable`, but it does not participate in auto-updates.

## Linux: packages for more distributions

Build on a Linux host with Node.js 22+ and npm. The DEB/RPM packages declare FFmpeg as a package dependency; AppImage users still need FFmpeg/ffprobe available on the host for MP4 export:

```bash
cd frame-studio-linux
npm install
npm run build:linux
```

The build produces an **AppImage** (recommended for broad distro compatibility and in-app updates), plus **DEB** for Debian/Ubuntu/Linux Mint and **RPM** for Fedora/openSUSE-compatible systems. Attach all three packages and `dist/latest-linux.yml` to the matching GitHub Release. Upload any extra files generated beside the AppImage if present.

For the widest glibc compatibility, build the Linux release on an Ubuntu LTS runner rather than directly on a very new Arch/CachyOS machine. On some distros the AppImage runtime needs FUSE 2 compatibility; if it reports `libfuse.so.2` missing, install the distro's FUSE 2 compatibility package or launch via the AppImage's extract-and-run option if supported.

The legacy Linux source ZIP remains installable with `install-linux.sh`, using system Electron when present. That source installation is not an AppImage and does **not** use electron-updater; it needs manual updates. MP4 export requires FFmpeg and ffprobe.

## Automatically build binaries when a GitHub Release is published

This kit includes `.github/workflows/release.yml`. To use it, commit the `frame-studio-linux/` source folder and the `.github/` folder to the `FRAME-Studio-Releases` repository's default branch. The workflow expects this exact folder layout. In GitHub, enable Actions and ensure the workflow token has **Contents: write** permission. Then:

1. Change `frame-studio-linux/package.json` version to the new version (for example `2.4.15`) and commit it before creating the release.
2. Create a GitHub Release with the matching tag `v2.4.15`.
3. The workflow builds Windows NSIS and Linux AppImage/DEB/RPM packages and attaches their updater metadata to that release.

Existing releases such as `v2.4.11` and the failed `v2.4.12` release are not changed. Manually install the first successfully published update-enabled installer/AppImage once; later compatible releases can update automatically.

## Tests

Run `npm test` in `frame-studio-linux` after dependencies are installed. These source tests cover editor code paths and updater configuration; they do not replace testing a packaged build on real Windows/Linux systems.


## Release notes and version tags (2.4.14+)

Use `.github/release.yml` to categorize GitHub-generated release notes by PR labels (`bug`, `feature`, `improvement`, `removed`, `compatibility`, and documentation/maintenance labels). Use `.github/RELEASE_TEMPLATE.md` as a checklist when writing release notes manually. GitHub category matching relies on pull-request labels; commits or unlabelled PRs may appear under “Other changes”.

The 2.4.15 source adds the categorized searchable Effects Library, Canvas-based Edge Blur / Inner Glow / Pixelate Blur / Directional Blur, deterministic Camera Shake, a floating Camera Preview, and a Three.js GLB/glTF import path. In the current 2.5D architecture, an imported model is rendered into a textured layer rather than inserted as native mesh geometry in the shared scene. Camera motion blur remains a screen-space temporal smear rather than per-pixel velocity blur. Runtime verification in real packaged Windows/Linux builds is still required before distributing binaries.
